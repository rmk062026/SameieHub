# Testing

- **Rammeverk:** xUnit (`tests/SameieHub.Tests`).
- **TDD** for forretningslogikk: test først → rød av riktig årsak → implementer → grønn → refaktorer.
- **Enhetstester** (Domain): `HousingUnitTests` (adresse, `AssignId`), `HousingUnitDetailsTests` (oppretting med bare adresse og med alle felt, oppdatering, normalisering, grenseverdier, ugyldige verdier, ingen delvis oppdatering, to eiere, aktivering/deaktivering, feilmelding uten verdi), `HousingUnitFilterTests` (søk og statusfilter), `BoardCaseFilterAndSortingTests` (søk, filtre, sortering), UI (M2D): `Web/BoardCaseListTests`, `BoardCaseCreateTests`, `BoardCaseEditTests` og `BoardCaseDetailTests` (oversikt og sortering, søk og filtre, statistikk, registrering, redigering med inaktiv boenhet, feltmeldinger, statusendring og avvisning av Vedtatt uten vedtak, vedtak registrert/korrigert/fjernet, gjenåpning, sletting med bekreftelse og Avbryt, blokkert sletting, databasefeil og manglende sak), `NorwegianDateFormatTests` (norsk tid, sommer/vinter), vedtaksdato (M2E) i domene-, tjeneste-, SQLite-, migrerings- og bUnit-testene (registrering med og uten dato, endring, fjerning sammen med vedtaket, ugyldig dato uten delvis oppdatering, uendret `UpdatedAt`, lagring etter omstart, migrering fra `AddBoardCases`-skjemaet) og snarveien fra boenhet (aktiv forhåndsvelges; inaktiv, ukjent og manglende ID gir ingen forhåndsvalg; knappen vises ikke for inaktive boenheter). bUnit leverer query-parametere via `NavigationManager.NavigateTo(...)` før komponenten vises; det brukes også for `?status=`-meldingene og to tester i `HousingUnitDetailTests` for styresaker på boenhetens side. `UiTestBase` (tidligere `HousingUnitUiTestBase`) setter opp fake-repositories, `TimeProvider` og begge tjenestene. Manuell kontroll (M2D, isolert database): registrering med alle felt, statusregelen, vedtak, filtre og søk, deaktivert boenhet, blokkert sletting av boenhet med styresak (ekte fremmednøkkel), sletting med Avbryt og bekreftelse, omstart med data intakt, og PC og mobil. `BoardCaseServiceTests` (tjenesten med `FakeBoardCaseRepository`, `FakeHousingUnitRepository` og `ManualTimeProvider`: registrering og Id, henting, oppdatering, statusoverganger, vedtak, tidsstempler ved endring/feil/uendret, kobling til aktiv/inaktiv/ukjent boenhet, bevart kobling til senere deaktivert boenhet, fjerning av kobling, sletting og ukjent Id), `BoardCaseTests` (inkludert `UpdatedAt` og `ToDetails`; opprettelse, standardverdier, UTC-krav, normalisering, grenseverdier, ugyldige endringer uten delvis oppdatering, statusregler, vedtak, valgfri møtedato og boenhetskobling, `AssignId`) og `HousingUnitServiceTests` (tjenesten mot `Fakes/FakeHousingUnitRepository`).
- **Integrasjonstester:** `Infrastructure/EfHousingUnitRepositoryTests` kjører mot ekte SQLite (ikke EF InMemory). `SqliteTestDatabase` lager en temp-fil per test via de samme migreringene som appen, og sletter den etterpå. Brukerens database i AppData berøres aldri. `RestartAsync()` simulerer omstart mot samme fil. `HousingUnitDetailsPersistenceTests` kontrollerer at alle felt, to eiere, fjerning av eier 2 og status lagres varig. `HousingUnitDeletionTests` dekker sletting (varig etter omstart, ukjent Id, eier- og kontaktdata fjernes, Id gjenbrukes ikke, blokkering ved simulert referanse; se begrensningen i ARCHITECTURE.md). Styresaker (M2C): `BoardCasePersistenceTests` (lagring, Id, henting, endringer, UTC og presisjon, tekst-enum, `DateOnly`, sletting), `BoardCaseRelationTests` (ekte fremmednøkkel: ugyldig referanse, blokkert og tillatt sletting av boenhet, bevart kobling til deaktivert boenhet, skjemaets `RESTRICT`), `BoardCaseMigrationTests` (tom database og M1F-database med boenheter og personopplysninger som er uendret) og `SqliteConstraintErrorsTests` (klassifisering av SQLite-feilkoder). `HousingUnitMigrationTests` oppgraderer en database fra første migrering med eksisterende rader og kontrollerer at de beholdes og er aktive.
- **UI-tester:** `Web/` bruker bUnit mot Razor-komponentene med fake repository (`FailableHousingUnitRepository` kan simulere databasefeil). Dekker liste (antall, sortering, filter, søk på begge eiernavn, tomtilstander), detaljside (alle felt, manglende verdier, eier 2 skjult/vist, aktivering), skjema (bare adresse, alle felt, eier 2 legges til/fjernes, feltmeldinger, retting etter feil) og databasefeil. Sletting: bekreftelse kreves, Avbryt sletter ikke, bekreftet sletting, blokkert sletting, databasefeil og allerede slettet. Ikke dekket av bUnit: `?status=`-meldingen (bekreftet manuelt), rendermodus og ekte tastatur/nettleser.
- **Manuell UI-kontroll (M1D, M1E):** appen startes mot en isolert database (`Database__Path`) og styres i nettleser: registrering med to eiere og feilmelding ved feltet, detaljside, deaktivering, søk og filter, redigering med fjerning av eier 2, omstart med data intakt og mobilvisning. Personlige data brukes aldri; testdata er fiktive.
- **Arkitekturtest:** `DependencyDirectionTests` vokter avhengighetsretningen.
- **Kjøring:** `dotnet test SameieHub.slnx`. CI kjører restore, build og test ved push til `main` og pull requests.
- **Navnekonvensjon:** `Metode_Scenario_ForventetResultat`.

**Museklikk i nettlesertesten (M2E):** knappene (inkludert «Slett», «Avbryt» og «Ja, slett permanent») ble klikket via elementreferanser, som verktøyet omsetter til koordinater og museklikk; resultatet ble kontrollert i DOM etterpå. Begrensninger: verktøyets `find` og `read_page` ser ikke alltid nylig tegnet innhold og må kjøres etter rulling; skjermbilder etter rulling kan vise blanke felt (mobil layout ble derfor kontrollert både med skjermbilde og med mål i DOM); tastaturvalg i nedtrekkslister virker ikke, så nedtrekkslister og datofelt ble satt med `form_input`.
